# 简介

punch-hole 在两个位于 NAT 之后的对端之间建立一条直连的 UDP 通路。库给两端的 NAT 做探测分类，与对端协商一个打洞策略并执行，最后把一个裸的 `tokio::net::UdpSocket` 交还宿主。

两个设计决定决定了库的全部形态。

**信令归宿主所有。** 对端发现和控制信道留在宿主应用里。库吐出不透明帧，宿主用自己的传输通道把它们转发给对端，对端回来的帧则直接喂回库。已经有自己 RPC 或隧道体系的系统，可以把打洞作为现有架构上的一个功能直接嵌进来。

**交付物是裸套接字。** 打洞成功后返回一个标准 UDP 套接字，上面没有任何包装层。业务层决定在上面跑什么，QUIC、KCP、Noise 还是私有协议都行。

## 四条原则

代码里的每个决定都遵守这四条原则。

- **自带信令（BYOS）。** 库内没有任何信令服务端或客户端代码。帧如何到达对端由宿主决定。
- **两个角色取代身份系统。** 一场会话只有发起方（Initiator）和应答方（Responder）。最接近身份的值只有每次尝试的 nonce，它给数据面的包打标签。
- **裸套接字交付。** 会话开过的所有套接字里，只有胜出者被交还，其余在函数返回前全部关闭，端口和描述符干干净净。
- **快速失败。** 每个阶段有自己的截止时间，整场会话有一条硬性时钟上限。失败返回一个指明阶段的有类型错误。

## 宿主需要承担的事

库覆盖一次尝试，尝试之外的事都归宿主：

- 一条有序、经过认证的信令信道，
- 跨尝试的重试策略，
- 打洞失败后降级中继的决策，
- 在交付套接字上运行的业务协议。

## 关于本书

本书同时服务两类读者，各部分的顺序方便新人从头读到尾。

1. **理解 UDP 打洞** 讲清问题本身。它从 NAT 的基本行为讲到生日攻击，库里的每个决定都能落到你熟悉的地面上。
2. **使用本库** 演示 API、信令桥和宿主职责。
3. **参考** 给出架构、协议、资源限制、配置与测试体系的细节，最后列出当前的能力边界。

本书有英文和中文两个版本，工具栏上的按钮可以在两版之间逐章切换。
